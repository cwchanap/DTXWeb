# HPA-690 — MusicXML Drum Chart Export Design

**Date:** 2026-11-02

**Status:** Draft, revised after GitHub design review and the Task 0 importer spike; timing encoding settled per the user-approved "proceed with caveats" ruling

**Linear:** [HPA-690](https://linear.app/cwchanap/issue/HPA-690/export-dtx-drum-charts-to-musicxml-for-musescore-and-guitar-pro)

**Delivery:** One PR for design, implementation and tests. This documentation-only draft PR becomes the implementation PR; no second PR.

## Goal and boundaries

Add **Export MusicXML** to the read-only `/preview/[id]` page. The currently displayed drum difficulty downloads as an uncompressed UTF-8 MusicXML 4.0 (`.musicxml`) file that can be imported into MuseScore 4 and Guitar Pro 8.

Reuse the existing notation/timing model, without a new dependency, backend, storage, GraphQL endpoint, Cloudflare job or standalone tool. The intended exchange preserves drum sounds, chord onsets, staff positioning, open/closed hi-hat noteheads, 3:2 tuplets, bar lengths and effective tempo changes. Exact VexFlow layout is not a goal.

## Existing boundaries

- `packages/common/src/lib/notation/model.ts` defines `NotationChart`, `NotationMeasure`, `NotationNoteEntry`, `NotationTuplet` and `NotationTempoEvent`; `TICKS_PER_WHOLE = 192`.
- `quantize.ts` currently collapses playable DTX lanes into visual `keys: string[]`. Bass (`13`) and left bass (`1C`) share the same `f/4` key and can be merged.
- `drumMapping.ts` is already the authoritative playable lane-to-staff mapping through `laneToStaff()`.
- `NotationView.svelte` is the only production reader of `entry.keys`: it passes the array to VexFlow. It can derive those keys from actual source lane IDs instead.
- `timing.ts` already supplies normalized `chart.tempoEvents`. The preview page owns `chart`, `title`, `artist`, `levels`, `selectedFileUrl` and `committedFileUrl`.
- `packages/dtx-web/src/lib/api/download.ts` already implements a Blob-to-download-anchor helper. Reuse that rather than creating another.
- The separate DTX-to-MIDI tool and `DTXFile.getMidiNoteNumber` use lane IDs `01`–`0C` rather than notation lanes `11`–`1C`; do not reuse those maps in this task.

## Confirm importer semantics early (Task 0)

Before committing to the model/writer encoding, construct a small **schema-valid** reference `.musicxml` file directly (without the exporter or UI) and import it into both target apps. Include:

1. Simultaneous `13` bass + `1C` left bass: two instrument IDs on the same `F4` staff position; listen for separate GM sounds.
2. A tempo change in the middle of a measure: compare a direction placed at an entry boundary (no offset) against one inside a rest (positive offset with `sound="yes"`).
3. An off-grid one-tick gap: compare the intended `<duration>` vs the visual `<type>` and confirm onset timing.
4. If possible, a small triplet example with a rest.

Record **observed** app/version/results or explicitly `unverified` in this PR. Do not assume Guitar Pro 8 handles `<midi-unpitched>` or direction offsets the same way as MuseScore. Use MusicXML 4.0 semantics as the default and adjust only from a reproduced failure. If apps are unavailable, continue standards-based implementation but do not claim either importer acceptance.

### Replace VexFlow keys with source lane IDs

```ts
export interface NotationNoteEntry {
	kind: 'note';
	startTick: number;
	durTicks: number;
	laneIds: string[]; // distinct, sorted playable DTX lanes at this onset
}
```

In `quantize.ts`, collect `Set<string>` of playable lane IDs per onset; no intermediate VexFlow keys. Continue ignoring non-playable lanes and `noteID === '00'`, and keep the existing start/duration, rest and triplet logic unchanged. Only the shape of note entries changes.

In `NotationView.svelte`, use `Array.from(new Set(entry.laneIds.map(id => laneToStaff(id)!.key)))` when creating a `StaveNote`. That reproduces the existing visual result: open/closed hi-hats remain separate; kick/left kick share one visible notehead but retain two exported MIDI sounds. Update typed fixtures and exact expectations together with the model change; do not maintain legacy `keys` support.

### Single drum map

Add `midi: number` and `instrumentName: string` to `DrumStaff` in `drumMapping.ts`. Preserve its existing `key` and short display `name`. Use the same entry for visual position, MusicXML instrument name and GM pitch.

| ---- | ------------- | ------------: | ----------------------: |
| `11` | Closed hi-hat |            42 |                      43 |
| `18` | Open hi-hat   |            46 |                      47 |
| `1B` | Pedal hi-hat  |            44 |                      45 |
| `12` | Snare         |            38 |                      39 |
| `13` | Bass          |            36 |                      37 |
| `1C` | Left bass     |            35 |                      36 |
| `14` | High tom      |            50 |                      51 |
| `15` | Low tom       |            48 |                      49 |
| `17` | Floor tom     |            43 |                      44 |
| `16` | Crash         |            49 |                      50 |
| `1A` | Left crash    |            57 |                      58 |
| `19` | Ride          |            51 |                      52 |

For each **used** lane emit matching stable `score-instrument`/`midi-instrument` IDs (`I-11`, etc.) in one `score-part id="P1"`; notes reference them with `<instrument id="I-11"/>`. Set `<midi-channel>10</midi-channel>`, `<midi-program>1</midi-program>` and **1-based** `<midi-unpitched>` per MusicXML spec. Also emit `<instrument-sound>drum.group.set</instrument-sound>` in each `score-instrument` — verified in Task 0: without it MuseScore 4.4.0 maps the part to a `grand-piano` instrument template (still channel-10 percussion playback), with it the part becomes a proper `drumset` instrument with identical notation and channel-10 GM routing. GP8 8.1.5 already maps the part to a full `drumKit` element set from channel-10/unpitched alone (GPIF model-verified); whether `drum.group.set` itself is GP8-safe is **unverified** — it changes nothing GP8 needs, but no successful GP8 import of an `instrument-sound`-bearing file was observed. Use five-line percussion clef, `<unpitched><display-step>...` and `<display-octave>...` from the existing key. `/x2` → `<notehead>x</notehead>`; `/x3` → `circle-x`; other keys → normal. XML-escape all metadata and text.

### Timing and musical encoding

- `divisions = TICKS_PER_WHOLE / 4 = 48`. Process entries in ascending `startTick`. For entry i, the **advancing** `<duration>` equals its effective written duration — the ticks of its `<type>` (dots included), multiplied by `normal-notes/actual-notes` when inside a `<time-modification>` group — **not** the raw gap to the next onset. For a chord, all notes carry that duration, but only the first advances the cursor.
- Visual `<type>` uses `entry.durTicks` (or the tuplet written base `slotTicks * 3/2`), with the existing preview-style largest representable value not exceeding that length — and constrained so that the **effective written duration** (type ticks, × `normal/actual` inside `<time-modification>`) never exceeds the span to the next onset (`nextEntry.startTick - entry.startTick`, or `measureTicks - startTick` for the last entry). For ordinary notes that means the raw `<type>` must fit the span; a 3:2 member legitimately writes a base 1.5× its slot because only the scaled 2/3 advances. If `durTicks` does not fit, emit the largest representable type that does. After the note, emit `<forward>` for the remaining ticks up to the next onset/measure end — the Task 0 `t7` encoding: `<forward>` accepts any positive integer, needs no `<type>` and renders invisibly; XSD-valid and MuseScore 4.4.0-exact at tick precision (every onset verified via MIDI export on a completed 192-tick bar containing a 1-tick leading gap and a complete 3:2 group). **User-approved caveat posture:** GP8's handling of forwards other than 24 ticks is unverified (the isolated all-typed control could not be imported in a windowless environment; the only sub-grid datapoint, t3, is confounded with an untyped note) — emit forwards at all sizes and document this rather than gating on it; do not claim GP8 success or impossibility. The residual rejections: a span < 3 ticks (finest supported written type) between consecutive onsets, or an equally short span between the last entry's onset and the barline (a final onset at tick 190 or 191 in a 192-tick bar has no representable written type, so no supported effective written duration) → a specific export error naming the measure and tick — never emit an untyped note, a mismatched duration/type, or a fake rest to cover it. **Task 0 verdict: `<duration>` must equal the effective written duration.** For ordinary notes that is the `<type>` tick count; for a 3:2 tuplet member it is `typeTicks × 2/3` (e.g. quarter type + 3:2 → `<duration>32</duration>` at divisions=48) — the equality is checked _after_ applying `<time-modification>`, and actual vs notated duration must be kept distinct in the writer. MusicXML nominally permits intended vs notated duration to differ, but both importers break on it: MuseScore 4.4.0 recalculates duration from `<type>` ("calculated duration not equal to specified duration → using calculated duration"), shifting later onsets and overflowing the measure ("Incomplete measure: Found 193/192" — hard import failure); Guitar Pro 8.1.5 opens without error but silently empties the affected measure(s) (GPIF-verified: measure voices empty). Omitting `<type>` is also invalid: MuseScore converts untyped notes to invisible rests (silent note loss) and GP8 corrupts the bar sum (240/192 ticks in its model; UI showed 5.0:4.0). A `<backup>` overlap fails in MuseScore too, and a hidden `48:47`-style `<time-modification>` still fails MuseScore (Incomplete measure). Never emit untyped notes, fake 1–2-tick rests, or overlapping backups to paper over a gap — reject explicitly instead.
- Validate strictly increasing entry `startTick`, positive advancing durations, and the measure total. Normal quantization starts at tick 0, but its sub-3-tick rest handling can leave a **leading gap**. When `first.startTick > 0`, emit tempo directions within `[0, first.startTick)` **before** `<forward><duration>first.startTick</duration></forward>`: the tick-zero direction has no `<offset>`, later leading-gap directions use a positive offset relative to cursor 0. A direction exactly at `first.startTick` follows the forward. `<forward>` is adopted for leading gaps of any size per the user-approved caveats decision — MuseScore-verified at tick precision including 1 tick; GP8 support for sizes other than 24 is unverified and documented, not gated. The forward plus all advancing note/rest durations must total `measureTicks`.
- `NotationTuplet` startIndex/count/slotTicks signals 3:2. Emit `<duration>` = the actual advance `slotTicks`, `<time-modification>` with 3 actual/2 normal and written `<type>` for `slotTicks * 3/2` — the duration/type equality rule applies after the ratio: `slotTicks === (slotTicks * 3/2) * 2/3` must hold exactly. Put tuplet start/stop on first/last tuplet entry, on first note of a chord (or rest). Test that usual aligned triplet spans match `slotTicks`.
- Choose the largest exact tick unit from quarter 48, eighth 24, 16th 12, 32nd 6, 64th 3; examples `192 → 4/4`, `144 → 3/4`, `168 → 7/8`. Fail on bar lengths these units cannot represent instead of inventing a meter.
- For each normalized tempo event, compute `eventTick = round(fraction * measureTicks)` and emit it exactly once in sorted order. **Boundary policy:** (1) `0 <= eventTick < first.startTick`: before the leading gap construct as above, with no offset at tick 0 and a positive `<offset sound="yes">eventTick</offset>` otherwise; (2) `first.startTick <= eventTick < measureTicks`: immediately before the entry whose **half-open** span `[entry.startTick, next.startTick)` contains it, omitting the offset at the entry start or using `<offset sound="yes">eventTick - entry.startTick</offset>` for an interior event; (3) `eventTick === measureTicks` (including a normalized `fraction === 1`): **after** the final advancing note/rest, when the measure cursor is at the barline, emit `<direction>` with **no offset** before the next measure begins. Preserve ordering relative to a separate next-measure tick-zero direction at the same absolute time; reject events outside `[0, measureTicks]`. Directions include the metronome mark and `<sound tempo="..."/>` in schema order. A positive offset affects playback only with `sound="yes"`. GP8 8.1.5 kept only the **last-declared tempo per bar, repositioned to bar position 0**, in the baseline's encoding (GPIF-verified) — the surviving mark is _moved_, so the effective tempo for the earlier part of that bar changes in GP8 (not merely fewer marks). Whether alternate placements (metronome-only, sound-only, offset-positioned) behave differently is untested — `t9-tempo` could not be imported (Task 0 report §9). Per the user-approved caveats decision the writer still emits all tempo directions — they are correct MusicXML and MuseScore-verified — with GP8's observed reposition/drop behavior documented as a known importer limitation, not claimed solved or universal.
- For malformed/inconsistent entry or tempo positions, fail with a precise message; do not silently shift notes or expand this feature into a general rhythm engine.

### Preview action

Add a localized button in the existing `status === 'ready' && chart` header, next to the level selector. It is naturally absent when loading/error; it does **not** depend on audio readiness. Disable only while `selectedFileUrl !== committedFileUrl` so a pending selection never exports the previously committed notation under the new label.

On click: serialize the current `chart`, build a UTF-8 `.musicxml` Blob and pass it to the existing download helper (rename/export `defaultTriggerBrowserDownload` as `triggerBrowserDownload`). Filename:

```text
<artist> - <title> (<committed level label>).musicxml
```

Look up the level label through `levels.find(level => level.fileUrl === committedFileUrl)`, **not** `selectedFileUrl`. Sanitize path separators/control characters and preserve Unicode. Add `preview.export_musicxml` and `preview.export_musicxml_failed` in `en.json`/`jp.json`; catch errors and toast without navigating or modifying the chart. Use only the existing download utility; do not add a fifth copy of the Blob/anchor code.

## Non-goals and follow-up note

No MusicXML import, batch export, `.mxl` compression, separate score builder, new music theory abstractions or broad DTX MIDI converter refactor. The currently separate DTX-to-MIDI tool appears to use incompatible lane numbering; this may warrant its own future task but is **outside HPA-690**.
